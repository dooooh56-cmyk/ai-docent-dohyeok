# AI 도슨트 팀 역할 가이드

- 작성일: 2026-11-03
- 대상: 백엔드 2명, 프론트엔드 3명, 팀장
- 함께 볼 문서: [개발계획서](개발계획서.md), [실행 방법(README)](../README.md), [API 약속](api.md)
- 아래 경로는 모두 `docent/` 폴더 기준입니다(예: `server/app.py` = `docent/server/app.py`).

개발이 처음인 팀원을 기준으로, 각자 무엇을 왜 하는지, 어떤 파일을 만지는지, 매주 무엇을 끝내면 되는지를 적었습니다. 처음부터 다 이해할 필요는 없습니다. **1장(공통)을 모두 읽고, 그다음 자기 역할 장만 읽으면 됩니다.**

## 1. 모두 함께 알아야 할 것

### 1.1 우리가 만드는 것 한 문장

외국인 관람객이 카메라·마이크·이어폰이 달린 글라스를 쓰고 조선 회화 앞에 서면, AI가 그림을 알아보고 **관람객이 아는 외국 그림과 비교하며** 영어로 대화해 주는 도슨트입니다.

### 1.2 꼭 알아야 할 용어

| 용어 | 쉬운 설명 | 우리 프로젝트에서는 |
| --- | --- | --- |
| 클라이언트 | 사용자가 직접 만지는 쪽 프로그램 | 아이폰 웹페이지(`static/`), 나중에는 글라스 앱 |
| 서버(백엔드) | 클라이언트의 요청을 받아 처리하고 답을 돌려주는 프로그램 | 노트북에서 도는 Python 프로그램(`server/`) |
| API | 클라이언트와 서버가 주고받는 약속(주소 + 보내는 내용 + 받는 내용) | `/api/session`, `/api/turn` |
| 요청 / 응답 | 클라이언트가 보내는 것 / 서버가 돌려주는 것 | 음성+사진을 보내면 답변 문장을 받음 |
| Gemini | 구글의 AI 모델. 글·사진·소리를 이해하고 글을 만들어 냄 | 받아쓰기, 그림 인식, 답변 생성을 한 번에 함 |
| 프롬프트 | AI에게 주는 지시문 | `server/prompts.py`의 `SYSTEM_INSTRUCTION` |
| 세션 | 한 관람객의 관람 한 번(시작~끝) | 프로필, 본 작품, 들은 비교를 기억 |
| 콘텐츠 DB | 도슨트가 말해도 되는 사실을 모아 둔 표 | `data/artworks.csv`, `data/comparisons.csv` |
| 지연(latency) | 말을 끝낸 뒤 답이 들릴 때까지 걸린 시간 | 화면 하단 `gemini ___ ms · total ___ ms` |
| 환각 | AI가 사실이 아닌 내용을 그럴듯하게 지어내는 것 | 콘텐츠 DB에 없는 사실을 말하면 환각 |
| 저장소(repo) / 브랜치 / PR | 코드를 모아 두는 곳 / 각자 작업 공간 / "내 작업을 합쳐 주세요" 요청 | GitHub `ai-docent-dohyeok` |

### 1.3 대화 한 번이 흘러가는 길

관람객이 버튼을 누르고 말한 뒤 답을 듣기까지, 각 단계를 맡은 사람이 다릅니다. **자기 칸이 어디인지 먼저 확인하세요.**

```text
① 관람객이 말함 ─────────── 폰/글라스 마이크          [FE1, FE2]
② 녹음 + 사진 한 장 찍기 ─── static/app.js, audio.js  [FE1]
③ 서버로 전송 (/api/turn) ── static/api.js, Cloudflare 터널 [FE1 ↔ BE2]
④ 세션 꺼내기 ──────────── server/session.py         [BE1]
⑤ 작품 정보 + 비교 고르기 ── server/content.py, data/  [BE1, FE3]
⑥ Gemini에게 묻기 ───────── server/gemini_client.py, prompts.py [BE1]
   (사진 → 어떤 그림인지 인식)                         [BE2]
⑦ 답변을 클라이언트로 돌려줌 ─ server/app.py            [BE1]
⑧ 영어 음성으로 읽어 줌 ──── static/audio.js          [FE1]
⑨ 이어폰으로 들림 ────────── 폰/글라스                 [FE1, FE2]
```

### 1.4 첫 주에 모두 할 일 (온보딩)

역할과 상관없이 **전원이 자기 노트북에서 v0를 한 번 실행**해 봅니다. 직접 돌려 봐야 위 그림이 이해됩니다.

1. GitHub 계정을 만들고 팀장에게 저장소 초대를 받습니다.
2. 설치: Git, [uv](https://docs.astral.sh/uv/)(Python 실행 도구), VS Code 같은 코드 편집기.
3. [README](../README.md)의 "준비"와 "실행"을 따라 서버를 켜고, 노트북 브라우저에서 `http://localhost:8000`을 엽니다.
4. 입력창에 "I'm from Japan and I like ukiyo-e"를 쳐 보고, 하단의 프로필이 바뀌는지 봅니다.
5. `server/prompts.py`의 `SYSTEM_INSTRUCTION`에서 "2-4 short spoken sentences"를 "1 sentence"로 바꾸고 서버를 다시 켜서 답이 짧아지는지 봅니다. **확인 후 원래대로 돌려놓습니다.**

> Gemini API 키는 팀장이 개인별로 나눠 주거나 각자 발급합니다. **키는 절대 GitHub에 올리거나 단톡방에 붙여 넣지 않습니다.** `.env` 파일에만 둡니다.

### 1.5 협업 규칙

- **브랜치**: 각자 `이름/작업내용` 브랜치에서 작업합니다(예: `minji/tts-speed`). 메인 브랜치에 직접 올리지 않습니다.
- **PR**: 작업이 끝나면 PR을 만들고, 같은 파트 1명이 읽어 본 뒤 합칩니다. PR 설명에는 "무엇을 바꿨고, 어떻게 확인했는지"를 씁니다.
- **매일 10분 공유**: 어제 한 일 / 오늘 할 일 / 막힌 것. 막힌 지 **2시간이 넘으면 무조건 공유**합니다. 혼자 하루를 쓰는 것보다 훨씬 빠릅니다.
- **매주 금요일 통합 시연**: 실제 폰(이후 글라스)으로 처음부터 끝까지 한 번 돌려 보고, 안 된 것을 다음 주 할 일로 옮깁니다.
- **API 약속 변경은 공지 후에**: `/api/turn`에 보내는 값이나 받는 값을 바꾸려면 BE1과 FE1이 먼저 합의합니다. 한쪽만 바꾸면 다른 쪽이 고장 납니다.
- **AI 코딩 도구 사용 가능**: Claude, Gemini 등으로 코드를 짜도 됩니다. 단, **이해하지 못한 코드는 PR에 올리지 않습니다.** "이 코드가 무슨 일을 하는지 한 줄씩 설명해 줘"라고 물어보고 이해한 뒤 올리세요.

| 역할 | 담당 | 한 줄 요약 | 주로 만지는 곳 |

| 팀장 | 일정·검증·대외 | 일정 관리, 콘텐츠 최종 확인, 박물관 협조 | 계획서, 체크리스트 |

## 3. BE1 — 대화 엔진

### 왜 필요한가

도슨트의 "두뇌"입니다. 같은 Gemini라도 무엇을 어떻게 물어보느냐(프롬프트)와 무엇을 기억시키느냐(세션)에 따라 답의 품질이 완전히 달라집니다.

### 쓰게 될 것

- **Python**: 서버 코드 언어
- **FastAPI**: 주소(`/api/turn`)로 요청을 받는 Python 도구
- **google-genai**: Python에서 Gemini를 부르는 공식 도구
- **JSON**: AI 답을 `{"reply": "...", "artwork_id": "..."}` 같은 정해진 형태로 받는 형식

### 지금 코드에서 먼저 읽을 곳

1. `server/prompts.py`의 `SYSTEM_INSTRUCTION`: 도슨트에게 주는 규칙
2. `server/gemini_client.py`의 `build_context()`: 작품 정보와 세션 상태를 AI에게 보낼 글로 만드는 부분
3. 같은 파일의 `DocentReply`: AI가 돌려줘야 하는 답의 모양
4. `server/session.py`: 관람객마다 무엇을 기억하는지

### 주차별 할 일

| 기간 | 할 일 | 끝났다는 기준 |
| --- | --- | --- |

### 주고받는 것

- **FE3에게서**: 대화 시나리오, 말투 기준, 평가 질문 세트 → 프롬프트에 반영

- **BE2에게**: 매 대화의 응답 시간과 인식 결과를 로그로 남겨 달라고 요청

### 자주 막히는 곳

- 프롬프트를 바꿨는데 반영이 안 됨 → 서버를 껐다 켰는지 확인

- "프롬프트를 바꿨더니 좋아졌다"는 느낌만으로 판단하지 말 것 → **항상 같은 질문 세트로 전후를 비교**

## 4. BE2 — 인식·데이터·운영

### 왜 필요한가

그림을 잘못 알아보면 아무리 좋은 설명도 틀린 설명이 됩니다. 또 CSV에 쉼표 하나만 잘못 들어가도 서버가 켜지지 않습니다. 시연 당일 서버가 멈추지 않게 지키는 것도 이 역할입니다.

### 쓰게 될 것

- **Python**, **CSV 파일 다루기**(`csv` 모듈)
- **사진 세트**: 회화실에서 찍은 그림 사진 + "이 사진은 어떤 그림" 정답 표
- **로그**: 서버가 한 일을 시간순으로 적어 두는 기록
- **Cloudflare 터널**: 노트북 서버를 아이폰에서 접속 가능한 HTTPS 주소로 열어 주는 도구

### 주차별 할 일

| 기간 | 할 일 | 끝났다는 기준 |
| --- | --- | --- |
| 11/5–11/11 | **CSV 검사 도구** `tools/check_content.py`(빈 자리만 만들어 둠, 찾아야 할 오류 목록은 파일 주석에 있음): 빈칸, 잘못된 ID, `|`·`;` 구분자 실수, 없는 작품을 가리키는 비교쌍 찾기 | FE3이 CSV를 고칠 때마다 실행해 오류 목록을 보여 줌 |

| 11/12–11/18 | (인식 정답률이 낮으면) **임베딩 매칭 실험**: 미리 찍은 기준 사진과 비교해 고르는 방식(계획서 5장 2안) | 지금 방식과 정답률·시간 비교표 |
| 11/19–11/25 | **현장 인식 테스트**: 회화실 실제 사진(조명, 유리 반사, 사람 가림)으로 다시 측정 | 현장 정답률 공유 |
| 11/26–12/1 | **시연 운영 준비**: 서버·터널 켜는 순서 체크리스트, 핫스팟 준비, 장애 시 대처 순서 | 다른 팀원이 체크리스트만 보고 서버를 켤 수 있음 |

### 주고받는 것

- **FE3에게서**: 작품 목록과 CSV → 검사 결과를 돌려줌

- **FE2와**: 글라스 카메라 사진 품질(해상도, 흔들림)이 인식에 미치는 영향 확인

## 5. FE1 — 클라이언트·오디오

### 왜 필요한가

관람객이 실제로 경험하는 것은 "버튼 누르고 말하기 → 답 듣기"입니다. 이 과정이 2초냐 8초냐, 소리가 잘 나오냐가 체감 품질의 대부분입니다.

### 쓰게 될 것

- **HTML/CSS/JavaScript**: 웹페이지의 뼈대, 모양, 동작
- **getUserMedia**: 브라우저에서 카메라·마이크를 켜는 기능
- **MediaRecorder**: 마이크 소리를 녹음하는 기능
- **speechSynthesis**: 글을 음성으로 읽어 주는 브라우저 기능
- **fetch / FormData**: 서버로 녹음과 사진을 보내는 기능
- **Safari 웹 속성(개발자 도구)**: 아이폰 화면의 오류를 맥에서 보는 방법

### 지금 코드에서 먼저 읽을 곳

`static/app.js`를 위에서부터 읽습니다. ①~⑤ 번호 주석을 따라가면 흐름이 보입니다: `start` 클릭 → 녹음 시작(`pointerdown`) → 녹음 끝(`onRecordingStop`) → 사진 찍기(`captureFrame`) → WAV 변환(`audio.js`의 `toWav16k`) → 전송(`sendTurn` → `api.js`의 `postTurn`) → 읽어 주기(`audio.js`의 `speak`).

## 6. FE2 — 글라스 연동

### 왜 필요한가

최종 시연은 폰이 아니라 글라스입니다. 글라스의 카메라 영상과 마이크 소리를 우리 서버로 보내고, 답을 글라스 이어폰으로 들려줘야 합니다. **가장 불확실한 부분이라 가장 먼저 조사를 시작해야 합니다.**

### 쓰게 될 것 (제품에 따라 달라짐)

- **제조사 SDK**: 글라스 회사가 개발자에게 주는 도구 모음. 이게 있어야 글라스 카메라에 접근 가능
- **iOS 앱(Swift)** 또는 **Android 앱(Kotlin)**: SDK가 대부분 폰 앱 형태로 제공됨
- **블루투스 오디오**: 글라스를 이어폰·마이크로만 쓰는 가장 간단한 방법

### 주차별 할 일

| 기간 | 할 일 | 끝났다는 기준 |
| --- | --- | --- |
| 11/5–11/11 | **조사**: 후보 상용 글라스별로 ① 카메라 영상을 개발자가 받을 수 있는지 ② 필요한 개발 도구 ③ 가격·구매 가능 여부 ④ 아이폰 지원 여부 정리 | 비교표를 팀에 공유하고 제품 결정 |
| 11/5–11/11 | **최소 대안 확인**: 글라스를 블루투스 이어폰·마이크로만 연결하고 폰 카메라를 목걸이처럼 걸어 v0 동작 | SDK가 안 될 때 쓸 수 있는 시연 방법 확보 |

## 7. FE3 — 대화 UX·콘텐츠

### 왜 필요한가

글라스에는 화면이 없어서 **대화 자체가 UI**입니다. 첫 인사, 질문하는 방식, 답의 길이, 비교를 꺼내는 순간이 모두 디자인입니다. 또 도슨트는 CSV에 적힌 사실만 말하므로, **CSV가 틀리면 도슨트가 틀립니다.** 이 역할이 프로젝트 품질을 가장 크게 좌우합니다.

### 쓰게 될 것

- **구글 시트 또는 VS Code**: CSV 편집
- **e뮤지엄, 국립중앙박물관 소장품 검색**: 조선 회화 공식 정보
- **해외 박물관 소장품 페이지**: 비교할 외국 그림 정보(예: 메트로폴리탄 미술관, 루브르 등의 공식 페이지)
- 코딩은 거의 없습니다. 대신 BE2가 만든 CSV 검사 도구를 실행하는 법을 익힙니다.

### 주차별 할 일

| 기간 | 할 일 | 끝났다는 기준 |

| 11/5–11/11 | **전시 목록 확정**: 조선 회화실에 지금 실제로 걸린 작품 목록 확인(현장 방문 또는 공식 사이트) | 작품명, 작가, 위치 목록 |

### 좋은 비교쌍의 기준

1. **관람객이 실제로 알 만한 작품**인가 (출신 국가·관심사와 연결)
2. 유사점과 함께 **차이점도 분명히** 말할 수 있는가
3. "영향을 받았다"가 아니라 **"비교해 보면 보이는 것"**으로 설명했는가 (근거 없이 역사적 영향 관계를 말하지 않음)
4. 유사점·차이점마다 **근거 출처**가 있는가

- 확인 못한 내용은 지우거나 `verification_status=unverified`로 남기기. 추측으로 채우지 않기
